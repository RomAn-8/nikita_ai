## Разделение ответственности

### `bot/handlers/`

Использовать для Telegram-слоя:
- чтение `update` и `context`;
- проверка входных данных;
- вызов сервисного слоя;
- отправка ответа пользователю;
- минимальная orchestration-логика.

В handlers нельзя держать:
- тяжёлую бизнес-логику;
- SQL;
- длинные преобразования текста;
- работу с файлами;
- сложную сборку промптов;
- смесь Telegram API, БД и файловых операций в одной функции.

### `bot/services/`

Использовать для бизнес-логики:
- работа с SQLite;
- работа с профилем пользователя;
- работа с памятью, контекстом и настройками чата;
- подготовка сообщений для LLM;
- логика, которую могут переиспользовать несколько handlers;
- игровая логика, если она не относится к Telegram API-слою.

Сервисы не должны зависеть от `Update` и `ContextTypes.DEFAULT_TYPE`, кроме специальных адаптеров.

### `bot/core/`

Использовать для базовых сущностей и каркаса системы:
- контекст агента;
- роутинг;
- ошибки;
- базовые промпты;
- общие интерфейсы.

### `bot/tools/`

Использовать для инструментов агента и интеграций, которые подключаются через общий реестр.

### `bot/utils/`

Использовать только для небольших переиспользуемых функций без собственной бизнес-модели.

## Особое правило для `bot/main.py`

`bot/main.py` — это composition root: точка входа, импортов и регистрации обработчиков.

Разрешено в `bot/main.py`:
- импортировать handlers и services;
- регистрировать `CommandHandler`, `MessageHandler`, `CallbackQueryHandler`;
- описывать `run()`, `post_init()` и инициализацию приложения;
- хранить только ту логику, которая уже исторически живёт в `main.py`, если задача именно исправляет её поведение.

Запрещено без явной необходимости:
- добавлять новую бизнес-логику в `main.py`;
- дублировать в `main.py` handlers, которые уже должны жить в `bot/handlers/`;
- создавать в `main.py` новые локальные функции `/start`, `/help` и других команд, если команда уже должна быть вынесена в handlers.

Если в проекте уже есть дублирование между `bot/main.py` и `bot/handlers/`, сначала определить, какой обработчик реально используется через регистрацию в `run()`, и менять именно его.

## Архитектурный долг проекта

В проекте есть важное расхождение:
- `bot/handlers/start.py` и `bot/handlers/help.py` могут быть мёртвым кодом;
- локальные `start()` и `help_cmd()` в `bot/main.py` могут перетирать эти импорты;
- нельзя по имени файла предполагать, что именно он используется.

Перед изменением `/start` и `/help` обязательно проверять:
- фактическую регистрацию команды;
- фактический источник текста ответа.

## Точки регистрации новой команды

При добавлении любой новой команды обязательно обновить все четыре точки. Без этого команда считается незавершённой.

| # | Файл | Функция | Что добавить |
|---|------|---------|--------------|
| 1 | `bot/main.py` | `start()` | Строку `/команда — описание` в список `lines` в нужной группе |
| 2 | `bot/main.py` | `help_cmd()` | Ту же строку в список `lines` в нужной группе |
| 3 | `bot/main.py` | `post_init()` | `BotCommand("команда", "Описание")` в список `cmds` |
| 4 | `bot/main.py` | `run()` | `app.add_handler(CommandHandler("команда", handler_func))` |

Если команда использует inline-кнопки (`CallbackQueryHandler`), добавить также в `run()`:

```python
app.add_handler(CallbackQueryHandler(callback_func, pattern="^prefix_"))
```

### Актуальные группы в `start()` и `help_cmd()`

Порядок сохранять:
- 🔧 Основные режимы
- 🤖 Специальные режимы
- ⚙️ Настройки
- 🧪 Тестирование
- 📚 RAG и эмбеддинги
- 🌤️ Погода
- 👤 Регистрация и записи
- 🎤 Голосовой ассистент
- 🤖 Локальные модели
- 🚀 Деплой
- 🎮 Игры
- 📖 Справка

`📖 Справка` должна оставаться последней.

## Как работать с задачами

Для каждой задачи соблюдать типовый цикл. Не перескакивать в код без понимания правильного места для изменения.

### Профили задач

Для каждой задачи сначала определить один профиль:

1. **Новая функциональность**
   - новая команда;
   - новый handler;
   - новый service;
   - новая интеграция;
   - новый инструмент в `bot/tools/`.

2. **Исправление бага**
   - исключение;
   - неправильное поведение команды;
   - поломка маршрутизации;
   - проблемы с БД, памятью, MCP, RAG, LLM-ответами.

### Стадии работы

Для обеих категорий использовать короткий обязательный цикл:

1. `Research` — понять, какие файлы уже есть и где должна жить логика.
2. `Plan` — кратко определить, что меняется и в каких файлах.
3. `Executing` — внести изменение в правильный слой.
4. `Validation` — проверить импорты, типы, очевидные ошибки, стиль, запуск.
5. `Report` — кратко зафиксировать, что сделано и какие ограничения остались.

Если задача связана с добавлением новой пользовательской команды, недостаточно только реализовать handler и бизнес-логику. Команда считается завершённой только если она:
- реализована в правильном слое;
- зарегистрирована в `bot/main.py` в существующем стиле проекта;
- добавлена в меню команд Telegram, если в проекте используется централизованная установка команд;
- описана во всех пользовательских точках входа, где перечисляются доступные команды: `/help`, `/start`, меню команд и другие справочные сообщения, если они есть в проекте;
- добавлена именно в тот источник текста, который реально используется зарегистрированным обработчиком.

## Импорты

Соблюдать порядок:
1. стандартная библиотека;
2. сторонние библиотеки;
3. локальные импорты проекта.

Не делать циклические импорты без крайней необходимости. Если логика переиспользуется между handlers — переносить её в `services/`, `core/` или `utils/`.

## Правила для handlers

Каждый handler должен быть тонким.

Обязательные принципы:
- сначала проверить `update.message` или другой нужный объект из `update`;
- валидировать аргументы до вызова сервисов;
- длительные действия сопровождать `send_action("typing")`, если это уместно;
- ловить ошибки на уровне handler и показывать пользователю понятное сообщение;
- логировать исключение через `logger.exception(...)`;
- вызывать сервисы, а не реализовывать всю логику прямо внутри handler.

Если в проекте есть одноимённые функции в `bot/main.py` и файлы в `bot/handlers/`, нельзя по имени предполагать, что используется именно файл из handlers. Сначала нужно проверить фактическую регистрацию команды в `run()`.

## Правила для services

- сервис должен содержать предметную логику, а не Telegram API-слой;
- все ошибки должны быть либо явно обработаны, либо проброшены вверх с понятным сообщением;
- операции записи в SQLite должны завершаться `conn.commit()`;
- SQL-запросы должны быть параметризованными;
- при работе с JSON и файлами нужно возвращать понятные ошибки, пригодные для показа пользователю или логирования.

## Работа с БД

- использовать единый доступ через `open_db()`;
- не открывать соединение с БД произвольным способом в новых модулях, если уже есть готовая точка входа;
- не дублировать SQL-логику по нескольким handlers;
- миграционные изменения делать аккуратно и идемпотентно по образцу `_ensure_column(...)`.

## Работа с конфигом

- настройки брать из `bot/config.py` и `.env`;
- не читать `os.getenv(...)` хаотично в новых модулях, если настройка уже должна жить в `config.py`;
- пути проекта должны быть централизованы.

## Работа с LLM / RAG / MCP

- доступ к OpenRouter и модели — через существующие модули (`openrouter.py`, сервисы, `core`);
- RAG-логику не дублировать в handlers;
- MCP-интеграции добавлять либо в отдельные `mcp_*.py`, либо в `bot/tools/`, в зависимости от текущего паттерна в проекте;
- при добавлении нового инструмента сначала проверить, не решается ли задача расширением существующего `registry.py` или `mcp_tools.py`.

## Типизация и документация

- для новых функций использовать `type hints`;
- у публичных функций и нетривиальных методов писать короткие `docstrings`;
- комментарии писать только там, где без них неочевидно, почему решение устроено именно так;
- избегать `Any`, если можно указать конкретный тип.

## Примеры хорошего стиля в этом проекте

### 1. Базовый интерфейс handler

Хорошо: общий базовый класс вынесен в `bot/handlers/base.py`, а создание контекста централизовано.

```python
class Handler(ABC):
    @abstractmethod
    async def handle(self, update: Update, context: ContextTypes.DEFAULT_TYPE) -> None:
        pass

    def get_agent_context(self, update: Update, context: ContextTypes.DEFAULT_TYPE) -> AgentContext:
        return AgentContext.from_telegram_context(update, context)
```

### 2. Работа с SQLite через единый helper

Хорошо: соединение с БД открывается централизованно через `open_db()`, где сразу настроены WAL, busy_timeout и создание директории.

```python
def open_db() -> sqlite3.Connection:
    DB_PATH.parent.mkdir(parents=True, exist_ok=True)
    conn = sqlite3.connect(DB_PATH, timeout=30)
    conn.execute("PRAGMA journal_mode=WAL;")
    conn.execute("PRAGMA synchronous=NORMAL;")
    conn.execute("PRAGMA busy_timeout=5000;")
    return conn
```

### 3. Идемпотентная миграционная логика

Хорошо: добавление новых колонок оформлено через `_ensure_column(...)`, а не через слепое `ALTER TABLE`.

```python
def _ensure_column(conn: sqlite3.Connection, table: str, column: str, ddl: str) -> None:
    cur = conn.execute(f"PRAGMA table_info({table})")
    cols = [r[1] for r in cur.fetchall()]
    if column not in cols:
        conn.execute(ddl)
```

### 4. Явная валидация и fallback при чтении профиля

Хорошо: сервис профиля создаёт дефолтную структуру и нормализует отсутствующие поля.

```python
if not USER_PROFILE_PATH.exists():
    default_profile = {
        "name": "",
        "interests": [],
        "communication_style": "",
        "habits": [],
        "preferences": {}
    }
    save_user_profile(default_profile)
    return default_profile
```

### 5. Логирование с понятным контекстом

Хорошо: исключения не проглатываются молча, а логируются с понятной причиной.

```python
except Exception as e:
    logger.exception("DB set model failed: %s", e)
```

## Шаблон типичного handler-файла

```python
"""Описание назначения handler."""

import logging

from telegram import Update
from telegram.ext import ContextTypes

from ..services.some_service import do_something
from ..utils.helpers import safe_reply_text

logger = logging.getLogger(__name__)


async def some_cmd(update: Update, context: ContextTypes.DEFAULT_TYPE) -> None:
    """Короткое описание команды."""
    if not update.message:
        return

    await update.message.chat.send_action("typing")

    try:
        result = do_something(" ".join(context.args))
        await safe_reply_text(update, result)
    except ValueError as e:
        logger.exception("Validation error in some_cmd: %s", e)
        await safe_reply_text(update, str(e))
    except Exception as e:
        logger.exception("Unexpected error in some_cmd: %s", e)
        await safe_reply_text(update, "Произошла ошибка. Попробуйте позже.")
```

## Шаблон типичного service-файла

```python
"""Описание назначения сервиса."""

import logging

logger = logging.getLogger(__name__)


def do_something(value: str) -> dict[str, str]:
    """Короткое описание функции."""
    value = value.strip()
    if not value:
        raise ValueError("Пустое значение недопустимо")

    try:
        return {"value": value}
    except Exception as e:
        logger.exception("Service error in do_something: %s", e)
        raise
```

## Validation перед завершением задачи

Перед тем как считать задачу выполненной, проверить:

- код положен в правильный слой;
- новые импорты корректны;
- нет явных циклических импортов;
- нет дублирования существующей логики;
- обработаны ошибки и пользователь получает понятный ответ;
- нет `print()` и отладочного мусора;
- нет захардкоженных секретов, токенов, путей;
- для записи в SQLite есть `commit()`;
- стиль кода совпадает с существующим проектом;
- если добавлена новая команда, она зарегистрирована в обработчиках;
- если в проекте есть меню команд, новая команда добавлена туда;
- если в проекте есть `/help`, новая команда описана в `/help`;
- если в проекте есть `/start` со списком возможностей или команд, новая команда отражена и там;
- проверены все пользовательские точки входа, где перечисляются команды, а не только одна;
- найден фактический источник текста `/start`, `/help` и других справочных сообщений, а не только файл с похожим именем;
- проверена фактическая регистрация команды в `run()` через `CommandHandler(...)`;
- если в `bot/main.py` есть локальная функция с тем же именем, что и импортированный handler, явно определено, какая реализация реально используется;
- команда доступна пользователю не только через ручной ввод, но и через интерфейс команд Telegram.

## Что делать, если задача не помещается в текущую архитектуру

Если запрос требует крупной переделки:
- сначала предложить минимально инвазивный вариант, совместимый с текущим проектом;
- не тащить новые архитектурные слои без необходимости.

Если в проекте уже есть скрытое дублирование обработчиков между `bot/main.py` и `bot/handlers/`, сначала нужно:
- указать на это как на архитектурный долг;
- определить, какой обработчик реально активен;
- исправлять активный обработчик;
- отдельно предложить безопасный рефакторинг для устранения дублирования, но не смешивать это с текущей задачей без явного запроса.

## Формат ответа

При выполнении задачи отвечать в таком порядке:
1. где правильно вносить изменение;
2. краткий план;
3. код / изменения по файлам;
4. что проверить;
5. краткий отчёт.

Не отвечать водой. Если информации недостаточно — прямо указывать это.

## Отчёт по задаче

После выполнения задачи кратко фиксировать:
- какие файлы изменены;
- что именно сделано;
- что проверено;
- какие риски или ограничения остались;
- если добавлялась новая команда, где именно она отражена: `bot/main.py`, меню команд Telegram, `/help`, `/start` и другие справочные сообщения;
- если затрагивались `/start` или `/help`, указать точный файл и функцию, из которых реально формируется текст ответа.

Если задача не решена полностью — честно указать, что именно осталось.
